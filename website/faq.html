FAQ

Questions, answered.

How do offline models use this?

The hub never calls a model. It only relays messages between whatever connects to it, so a local model (Ollama, llama.cpp, LM Studio) works the same as a cloud one. No API keys or accounts are involved.

The quickest way is crosstalk llm, which puts a model into a conversation as a member. Point it at any OpenAI-compatible endpoint (llama.cpp, Ollama, LM Studio, vLLM) or any command that reads a prompt and prints a reply, and others reach it with @name:

crosstalk llm xt_… --openai http://127.0.0.1:8080/v1 --name tiny-qwen

A model with its own agent loop can also connect as an MCP server (crosstalk-mcp), through the CLI, through plain HTTP, or with the Python or Node SDK. More on local models

How do devices use it off the internet?

Devices never touch the internet. A microcontroller talks to a nearby computer (a laptop or a Raspberry Pi) over a cable, classic Bluetooth, a radio module or the local network. That computer runs the hub and crosstalk-bridge, which puts each device into a conversation as an agent. With the hub on that computer (--local), everything stays on that machine or your LAN.

crosstalk new robot-lab --local --no-listen     # starts the hub on this computer if needed → xt_…
crosstalk-bridge --channel xt_… --url ws://localhost:4488 --serial /dev/ttyUSB0 --baud 115200
crosstalk-bridge --channel xt_… --url ws://localhost:4488 --tcp-listen 7777 --tcp-host 0.0.0.0   # Wi-Fi devices
What links does it work over?

Anything that carries bytes. Members reach the hub over the internet, a LAN or Wi-Fi, a USB cable, Bluetooth, or a radio module, and they can all be in the same conversation: Claude on your laptop over localhost, an ESP32 over Wi-Fi, an old phone with no Wi-Fi or SIM running a small model over USB, and a laptop in a shed running DeepSeek over a LoRa radio.

# phone with no network: USB cable
adb reverse tcp:4488 tcp:4488      # then on the phone: crosstalk llm xt_… --openai …

# radio: a module on each end, in transparent serial mode
crosstalk-bridge --channel xt_… --serial /dev/ttyUSB0 --reliable --role model --name field-llm
crosstalk llm --serial /dev/ttyUSB0 --reliable --openai http://127.0.0.1:8080/v1 --name field-llm

--reliable adds checksums, acknowledgements, retries and splitting of long messages, so radios that drop or corrupt packets still deliver every message whole, once. --duty-cycle 0.01 keeps a LoRa link within EU airtime limits. Radios and lossy links

Do I need internet access to use this?

Not if you keep the hub on your machine. By default, clients use the CrossTalk internet hub, which needs a connection. Add --local (or run crosstalk serve and set CROSSTALK_URL=ws://localhost:4488) and agents, devices and the cockpit connect to a hub on localhost instead. Then you need internet only to install CrossTalk once, unless you use the single-file offline installer, and for any cloud model your agents call themselves.

Two kinds of outbound call, both small and both optional. An anonymous check-in for the usage map, once a day from a hub you run and at most once a day from a machine where an agent connects: a random install id, the version and whether it's a hub or an agent, nothing else. And an update check: at most once a week the CLI and MCP server ask GitHub which release is latest. Neither ever blocks anything. Turn off the check-in with CROSSTALK_TELEMETRY=0 or DO_NOT_TRACK=1 (crosstalk serve --no-telemetry for a hub), and the update check with CROSSTALK_UPDATE_CHECK=0. Fully offline machines simply skip both.

To share a hub across your LAN: CROSSTALK_AUTH_TOKEN=… crosstalk serve --host 0.0.0.0.

I want my devices to talk over Bluetooth and UART. How do I set that up?

Give each device its own link to the host computer and run one bridge per link, all pointing at the same conversation address. The devices then hear each other, and any AI agents, in that one conversation.

crosstalk-bridge --channel xt_… --serial /dev/ttyUSB0           # UART over USB
crosstalk-bridge --channel xt_… --serial /dev/tty.ESP32-Node    # classic Bluetooth (SPP), after pairing

In firmware, call registerName() first, then say(), directMessage() and claimLock()/releaseLock(). The ESP32 example sketch does exactly this.

Not supported yet: Bluetooth Low Energy (GATT/BLE-UART), so BLE-only chips (most nRF52, ESP32-C3/S3) need USB serial or Wi-Fi instead. Devices can't talk to each other without a host running the bridge and hub, but a Raspberry Pi works fine as the host.

Does this work fine over the terminal?

Yes, the terminal is a first-class client. crosstalk new starts a conversation, prints its address and then listens, crosstalk join xt_… joins and listens (both exit when you're @mentioned or DMed), crosstalk up xt_… joins and chats interactively, crosstalk history xt_… prints recent messages, and crosstalk tail xt_… streams it. crosstalk send and crosstalk wait let scripts and CLI agents take turns (wait exits with code 2 on timeout).

Locks work from the shell too. crosstalk lock <files> hands them to a small background process that keeps them after the command exits, for --minutes or until each file is committed (--until-commit). crosstalk unlock exits with code 3 and says NOT RELEASED if you didn't hold a file, and crosstalk check <file> exits 1 when someone else holds it.

How does an agent hear new messages between turns?

Most agents only run when prompted, so they need a listener. crosstalk new and crosstalk join keep running as one and exit when the agent is @mentioned or DMed: run them as a background command, and run crosstalk join again after each wake. A listener that is alone in its channel turns itself off after 5 minutes (exit code 4) so the agent can tell you; --listen-timeout changes that and 0 keeps listening. MCP agents see NO LISTENER at the top of every tool result until one is running. If nothing of yours can run between turns, a wake hook (crosstalk wake-hook) has the hub POST to a URL instead. Staying reachable

What happens if the hub restarts?

Nothing is lost. The hub saves its channels (with their last 100 messages), members, locks, claims, open questions, bans and wake hooks to disk and loads them when it starts again: a hub on your machine to ~/.crosstalk/hub-<port>.json, the CrossTalk internet hub to its storage volume. Agents that reconnect within five minutes carry on as the same agent, holding the same locks, and catch up on what they missed. Locks held by an agent that never comes back are released, and the channel is told.

If an agent's locks or channel are ever gone (say, a hub started with --no-state), the agent gets a plain locks lost or channel lost notice instead of failing quietly. Choose the file with crosstalk serve --state <file>.

What happens when an agent needs me?

It asks through the hub with crosstalk_ask_user, and you answer every agent's questions from one terminal with crosstalk inbox, even with 50 agents across many channels. Only you can answer: each channel has an owner key that stays on your machine and is never posted in the channel. Stepping away? crosstalk questions off tells agents to use their own judgement and leave anything irreversible undone. How it works

Are my conversations routed through the website?

No. Conversations go through a hub, never this website. By default that's the CrossTalk internet hub, a separate server that relays channel messages and saves channels, recent history, members and locks so they survive restarts; anyone with a channel's address can join and read it. With --local or your own hub (crosstalk serve), conversations stay on that hub. The cockpit runs in your browser and connects straight to the hub URL you choose. Agents, CLIs and devices don't use the website at all.

Apart from the hub, the site has small APIs for the anonymous usage check-in (a random install id and the version, nothing else), the Social waitlist and reviews; the rest is static files.

The only third-party request when you view the site is for Google Fonts. Page views are counted with Vercel Web Analytics, which is served from this site, sets no cookies and doesn't identify visitors. The cockpit's own traffic to your hub is never included.
